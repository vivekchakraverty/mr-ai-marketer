Scheduling a post with an image you generated in the app now works. It previously refused,
with a message saying the posting engine could not reach this machine — which was true, and
this release makes it untrue.

## What was actually wrong

Posts sent from Distribute are handled by an automation engine running in a container, and
it attaches a picture by *fetching* it. The only copy of a generated image lives on this
machine, behind a backend that listens on `127.0.0.1` — which, inside a container, means the
container itself.

The container needed to be told where this machine is. The configuration to do that was
already written, and it was reading a value that nothing ever set, so it silently fell back
to a default that its own comment describes as the wrong one.

Measured on a real install, since this is a question about a running system rather than
about the code:

| Route | Result |
|---|---|
| The default that was in use (`host-gateway`) | No connection at all |
| The correct address, injected on each launch | Image fetched, byte-for-byte identical |

The address is assigned fresh every time the virtual machine restarts, so it is now looked
up and written on **every** launch — deliberately unlike the encryption key stored beside
it, which must never change or previously connected channels stop working.

## The image is sent as a private link that expires

The picture is not uploaded anywhere. The engine is handed a signed link that only it can
use and that stops working shortly afterwards. A scheduled post extends the link's life to
cover the wait, because it fetches the image when it runs rather than when you queue it.

## A narrower door, on purpose

The straightforward fix would have been to let the backend accept connections from anywhere.
That works, and it would also put every part of this app on your local network with a single
token in front of it — a wide change to fix one image fetch.

Instead there is now a second, very small listener that serves **only** signed image links,
and only on the virtual adapter the container sits behind. Traffic from your actual network
arrives on a different interface and never reaches it. The main app is untouched: still
`127.0.0.1`, still behind its session token.

It also only opens while the distribution engine is running, and closes when the engine
stops. If you never use Distribute, no extra socket is ever opened.

Tests cover the fetch, a forged signature, an expired link, a path-traversal attempt, and —
the one that protects the design — that the rest of the app answers nothing on that socket.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
