## Fixed: a generated post arrived in the Library twice

Writing a post on the Bluesky or Mastodon screen and then sending it to the Library produced
two near-identical cards — one titled with the opening line of the post, one titled
"Bluesky post · <niche>". Only the text was the same; the tags and the picture were on one of
them.

The cause was two save paths that did not know about each other. Both composers file a Library
row as they generate, so the draft is kept even if you navigate away. The **Send to Library**
button then wrote a second row for the finished composition. The Save button on the same screen
already avoided this — it recognises the row the generator filed and offers to open it rather
than saving again — but the composition button did not.

Sending a composition now finishes the row the generator already filed, adding the tags and the
attachment to it. Saving again after changing the tags updates that same entry rather than
stacking cards, and a fresh generation gets a new row of its own. Entries already duplicated by
the old behaviour are left alone; delete the bare-text ones by hand.

## Changed: a video is attached once, in the composer

The composers and the Distribute dialog each had their own **Upload video** button, and the two
were not connected. A clip chosen while writing the post reached Send to Engage and nothing
else — it was not kept with the post, so distributing that post later meant finding the same
file on disk and picking it a second time. The dialog's button was in fact the only way a video
ever reached Distribute.

The composer is now the one place a video is chosen. The clip is kept with the post as the
Library entry's attachment, plays in the entry itself, and arrives already attached in the send
dialog. The dialog's upload button is gone.

The clip shares the single file slot the generated picture uses rather than getting one of its
own, which is sound because a post carries one embed — the same reason a send has always
refused an image and a video together. In the dialog, choosing an image supersedes the attached
clip for that send instead of being rejected as a conflict; clear the image and the clip comes
back.

Two limits worth stating. Alt text is still typed where it is used, so a video distributed from
the Library takes its description in the send dialog. And a clip chosen on the Tumblr screen is
not carried, because distribution does not accept video on Tumblr — carrying it would produce
an entry whose attachment no channel could send.

## Added: Send History plays the attached video

A video in Distribute's "What was sent" panel was a file path. Confirming a scheduled post went
out with the right cut meant reading a UUID and opening the file yourself.

The clip now plays in the history card, alongside the image preview that was already there.
Nothing autoplays and nothing loads until you open the card. A clip that has since been deleted
off disk says so and shows its path, which by then is the only remaining answer to which file it
was.

## Verification

The complete backend suite passes: **259 tests**. Four new tests cover the Library's single file
slot — a clip filed as an entry's attachment, a clip finishing a row the generator filed, a clip
from outside the app's own output tree refused, and an image and a clip named together refused.
Four more cover the duplicate fix, including that finishing a generation row leaves exactly one
entry and that the update path applies the same containment check as the save path. Electron's
main process and renderer pass TypeScript checking, and the production desktop bundle builds
successfully.

No live social post was made while verifying this release.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
