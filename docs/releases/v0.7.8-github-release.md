Attached media now reaches the social timeline — for scheduled posts as well as immediate sends.

## Fixed: Send History showed media that the published post did not have

Distribute could show the text, hashtags and attached image or video correctly, then publish
only the words. The history row was displaying the durable app-local payload, while the final
posting boundary could lose the file without changing the job to Failed.

Local media is now prepared again at the moment a post is handed off. If the file has gone
missing or cannot be fetched, the send fails with an attachment error instead of becoming a
misleading text-only success. This applies equally to a post sent now and one that has waited
in the scheduler.

## Fixed: Mastodon's connector could drop images and videos

The bundled Mastodon automation connector constructs its multipart upload without the required
boundary. Images were rejected with HTTP 400; videos could resolve to an empty File input and
still create a status with no attachment.

Mastodon media posts now use the app's native uploader — the same transport already exercised
by the Mastodon composer. The active account token remains encrypted at rest in Electron's
operating-system-protected settings and is handed to the scheduler in memory on each launch.
The backend does not persist another copy.

An upload is not marked Sent merely because the status endpoint answered successfully. The
returned Mastodon status must contain a media attachment. If a server ever creates the status
without one, the app removes that incomplete post and records a failure.

## Fixed: Bluesky video sends were rejected before upload

Bluesky's action expects `imageUrls` to be an array even when the post contains a video and no
images. A missing webhook property became an empty string, so the action rejected the post with
"Expected array, received: \"\"". Every Bluesky payload now carries the correct empty array
when there are no images, including older scheduled jobs upgraded at send time.

## Fixed: rapid sends could be matched to the wrong automation run

Two posts sent close together could both be associated with whichever flow run happened to be
newest. Each delivery now carries a private job marker, and only the run whose webhook body has
that marker can update the history row. One post can no longer borrow another post's success or
failure state.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
