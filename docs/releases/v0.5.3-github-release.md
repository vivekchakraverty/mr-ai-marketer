Generated images stop disappearing, and Distribute learns to attach one — with an
honest limit on which ones.

## Generated images are kept

An image made in a post creator existed only as a URL on the screen that made it.
Close the screen and it was gone: still on disk, but with nothing pointing at it.

Each one is now saved to the Library as it is created, with **the approved prompt as
its text and the PNG as its file**. Open it and you get the picture and the words
that produced it, with the prompt editable like any other entry — so *"nearly right,
but wider"* is a small edit rather than a fresh start.

Titled by the post rather than the prompt, because that is what you recognise on the
shelf.

## Distribute can attach an image

Posts went out as text. Only Instagram had an image field, because only its flow had
one wired.

Four more channels now carry an image — **Bluesky, Mastodon, LinkedIn and Discord** —
using the field each platform's integration actually exposes. The send dialog offers
the images already on your Library shelf as thumbnails, plus a box for any public
image URL, and tells you which of your selected channels will actually carry it.

### What does not work yet

> **An image generated on this machine cannot be attached.** The dialog says so and
> refuses it, rather than queueing a post that fails while trying to download it.
> A pasted public image URL works normally.

The reason is plumbing, not policy. The posting engine runs inside its own container
and fetches an image over the network to attach it — and it cannot reach this app,
which listens only to itself. That was measured by starting the whole stack and
trying every route, not assumed: the standard address for "the machine outside the
container" points somewhere else entirely on this setup, and answered nothing.

The mechanism underneath is finished and proven — a container did fetch a real image
through it, byte for byte, once pointed at the right address. What remains is finding
that address automatically (it changes each time the machine boots) and listening on
it. That is the next release.

## Under the hood

Files the app generates are served behind the same session token as everything else,
which is why another program cannot simply fetch one. Attaching an image needs
exactly one file readable by exactly one other process, so this release adds
**signed, expiring links**: each names a single file, carries an expiry, and is
refused if it is forged, stale, or points anywhere outside the generated-output
folder. A link for a scheduled post outlives the wait.

Also added: a test that simply starts the application. A missing import took the
backend down at launch while the test suite stayed green, because every test imported
the parts it exercised directly and nothing imported the whole app.

## Upgrading

Nothing to migrate. Images you generate from now on appear in the Library
automatically; ones made before this release stay where they are.
