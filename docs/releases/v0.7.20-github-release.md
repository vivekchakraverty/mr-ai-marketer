Scheduled Mastodon and Bluesky posts can now go out while the app is closed, and there is a
walkthrough for connecting your accounts the first time you open it.

## Added: posting while the app is closed

A post scheduled for 3am only went out if the app happened to be running at 3am. The
scheduler lives inside the app, and the posting engine it drives is a container that stops
when the app does — so a send queued on Tuesday would simply not happen on Wednesday.

Setup now offers to create a **poster in your own Hugging Face account**: a small service that
holds your queue and publishes it on time, whether or not anything is running on your machine.
Scheduled Mastodon and Bluesky posts go there. Everything else is unchanged.

**It is yours, not ours.** The Space is created in your account and built from the poster that
ships inside this app — not copied from one we host. Your credentials are stored as that
Space's own secrets. Nothing of yours is ever held by us, and no two people share a poster.

**The credentials it holds are deliberately narrow.** For Mastodon it asks for a *second*
application scoped to `write:statuses` and `write:media`, and checks it really cannot read
your account before accepting it. For Bluesky it takes a session that renews itself rather
than your app password, which never leaves your machine — revoking the app password ends the
session too.

### About timing, honestly

On Hugging Face's free tier a Space sleeps when idle, and a free Space cannot be told not to.
So the promise is **normally on time, worst case late, never lost**: every pass publishes
everything whose time has *passed*, not only what is due that minute, so a poster that wakes
at 07:00 still sends the 03:00 post. The app wakes it when something is nearly due, and the
setup screen suggests a free pinger (cron-job.org) if you want the window tighter. Upgrading
the Space to paid hardware removes the sleeping entirely.

### It cannot post twice

A post handed to the poster is invisible to the local scheduler — ownership moves rather than
being shared — and each post carries an idempotency key the network itself honours. Retrying
a post the poster already sent is refused rather than repeated, and cancelling one it has
already picked up says so instead of silently failing.

If the handover fails for any reason, the post stays on the local scheduler exactly as before.
It is never lost; it just needs the app open.

## Added: a setup walkthrough

There was no first-run experience at all — the README told you to open Settings and find
things. New installs now get a walkthrough that goes through the accounts one at a time, with
a link straight to the page where each credential is created.

Every step can be skipped, it remembers where you stopped, and **Settings → Setup walkthrough**
reopens it whenever it suits. An install that is already set up is left alone.

## Fixed

- **Settings' "Save everything" could revert things changed elsewhere.** It wrote back the
  whole settings snapshot taken when the screen opened, so a credential connected from another
  screen in the meantime was overwritten with the older value.
- **The distribution engine's status and the cloud poster's credentials are now applied
  without restarting the app.** Both were read only when the backend started.
- **Health monitoring** learned about the poster Space, reporting a sleeping one as a note
  rather than a failure.

## Verification

The complete backend suite passes: **330 tests** locally, and **329 passed with 1 skipped**
against a virtual environment built to match continuous integration's dependency list exactly.
Electron's main process and renderer pass TypeScript checking, and the production bundle
builds.

Beyond that, this release was tested against Hugging Face itself rather than only in the
suite: a real Space and private dataset were created from the walkthrough, both networks were
connected to it, and the app was confirmed reading the poster's status and its queue back over
the network. Three defects were found that way and fixed — none of them was reachable from the
tests, which is why the check was done.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
