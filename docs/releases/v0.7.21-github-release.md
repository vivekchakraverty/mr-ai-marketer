Cloud posting works. 0.7.20 introduced it and it could not actually deliver a scheduled post —
this release is the six fixes that make it do what it said.

If you set up cloud posting on 0.7.20, **update and re-run Settings → Cloud posting → Reconnect
credentials → Repair this Space.** The poster running in your Hugging Face account is a copy of
the code from the version you installed, so it needs re-uploading to pick this up.

## Fixed: scheduled posts never went out at all

The poster checked its queue only when the queue had *changed*. But a post becomes due through
the passage of **time**, not because anything was added — so the check that ran when a post was
queued saw nothing due yet, remembered that, and every check afterwards returned early. The
scheduled hour arrived with nothing left looking.

This affected **every** scheduled post, Mastodon and Bluesky alike. Two real posts were lost to
it before it was found. The check now waits until either the queue changes or the soonest post
in it actually comes due.

## Fixed: video posts to Bluesky could not succeed

Bluesky does not take a video the way it takes an image. Video goes to a separate service that
transcodes it and only then returns something a post can embed; 0.7.20 uploaded video as an
ordinary attachment, which is accepted and then refused when the post is written.

Five distinct things were wrong along that path, and all five are fixed: the upload route
itself, the audience and the scope of the permission token the video service requires, the
reading of its reply, and the record key — which for a Bluesky post must be a timestamp
identifier rather than any unique string.

Mastodon video was unaffected and continues to work.

## Fixed: failures reported a code instead of a reason

Bluesky returns both a short code and a sentence explaining the problem. Only the code was
being kept, so a post that failed said `InvalidRequest` and nothing else — true, and useless.
Both are now shown.

This is the fix that made the others possible. As soon as the sentence came through, the
remaining failure named the exact field that was wrong.

## Unchanged: a retry still cannot post twice

Worth stating, because the record key changed. A Bluesky post's key is derived from the job it
belongs to and does not vary between attempts, so re-sending writes over the same post rather
than making a second one.

## Verification

The complete backend suite passes: **340 tests** locally, and the same against a virtual
environment built to match continuous integration's dependency list exactly. Electron's main
process and renderer pass TypeScript checking, and the production bundle builds.

Ten of those tests are new and cover the poster itself, which had none before and held every
defect in this list. They pin the timing check that lost the two posts, the permission scope,
and both properties of the record key — that it is a valid identifier, and that it is the same
one every time.

The real verification was not the suite. A scheduled post carrying a 27.6MB video was published
to Mastodon and to Bluesky by the poster, from the queue, at the time it was scheduled for.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
