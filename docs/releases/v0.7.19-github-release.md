A posting fix: a video attachment could not be uploaded before its own deadline expired — and
a way to send a post again when one still does not go out.

## Fixed: attachments were uploaded under a timeout meant for a small JSON request

A 29MB video attached to a Mastodon post failed with:

```
SSLError(SSLWantWriteError(3, 'The operation did not complete (write) (_ssl.c:2427)'))
```

That reads like a problem with the encrypted connection, and it is not one. It is a write
deadline expiring in the middle of the upload, which Python reports as the pending want-write
rather than as a timeout — which is why the real cause was not obvious from the message.

Both upload paths, Mastodon's and Tumblr's, sent their attachment under the same flat timeout
a small JSON request gets: 20 seconds and 25 seconds respectively. That is not a budget for
the call as a whole. The socket is armed with the connect timeout before the request body is
handed over and only relaxed afterwards for the reply, so the entire file has to leave the
machine inside that one window — and passing a separate read timeout does not move it.
Clearing 20 seconds with 29MB needs a sustained 12Mbit/s uplink held without a stall; the
100MB video Tumblr accepts would need 34Mbit/s. Images were never affected, being small
enough to fit either way.

The budget is now derived from the size of the file instead of being fixed: a pessimistic
floor speed, a base that still covers connecting and the handshake, and a ceiling so a
transfer that has stalled outright cannot hold a post open forever.

| Attachment | Before | After |
| --- | --- | --- |
| 1MB image | 20s | 68s |
| 29MB video | 20s | 291s |
| 100MB video (Tumblr's limit) | 25s | 860s |

The largest video Tumblr accepts is deliberately inside the ceiling, so the limit the app
enforces is postable on its own terms rather than clipped by it.

Both failure messages now name the file, its size, and how long was waited. The Mastodon one
used to call a video "the image" and reported neither number.

## Added: Try again, for a post that failed

Distribution history was read-only. It showed the error and left rebuilding the post by hand
as the only way forward — reasonable while a failure meant the content was wrong, and not
reasonable for the failure above, where the post needed no editing at all, only sending again.

Opening a failed post in history now offers **Try again**, which sends the same text and the
same attachment again.

It re-sends on the same row rather than filing a copy, so history stays one entry per post
rather than accumulating one per attempt. That also keeps the original idempotency key, which
is what lets the server recognise a repeat: an upload can fail leaving the post genuinely
unsent, but a reply lost on the way back looks identical from the app's side, and re-sending
under the original key is what stops the second attempt becoming a second post.

Only a failed post offers it. A scheduled one still has cancel, a sent one must not go twice,
and anything mid-flight belongs to the scheduler. If Mastodon is not connected, the retry is
refused before the stored error is disturbed. Because the app waits for the whole delivery —
minutes, for a post carrying video — the button stays visibly busy while it runs.

## Verification

The complete backend suite passes: **311 tests** locally, and **310 passed with 1 skipped**
against a virtual environment built to match continuous integration's dependency list exactly.
Electron's main process and renderer both pass TypeScript checking.

The Mastodon fix was confirmed against the live API rather than only in tests: the 29MB clip
that produced the error above was re-sent with the new button and published with its video
attached — 1920x1080, 50 seconds — which the previous release could not do at any uplink speed
most people have.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
