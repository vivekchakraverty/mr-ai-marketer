A Bluesky post of exactly 300 characters could be rejected for exceeding 300 characters.
This release makes the app count what the send path actually counts, and stop a post that
cannot go out before it goes out.

## Fixed: Bluesky rejected posts that were within its limit

Sending a 300-character post to Bluesky could fail with "Post text cannot exceed 300
characters" — a failure that reads as nonsense, arrives only after the post has been handed
off, and gives no clue what to cut.

The bundled Bluesky connector is measuring the wrong thing. Bluesky's rule is 300 *graphemes*.
The connector builds an `atproto` `RichText` and tests `RichText.length` against 300, and that
property is the **UTF-8 byte length** — the grapheme count is a separate `graphemeLength` the
check never reads. So every character outside plain ASCII spends two or three of a budget the
app was calling 300 characters. The post that prompted this was 300 characters and 306 bytes:
three curly apostrophes, each costing three bytes instead of one. Bluesky itself would have
taken it.

Bluesky's length is now measured in UTF-8 bytes everywhere the app shows it — the composer's
counter and the send dialog's — because that is the limit that is really enforced. Both read
"bytes" rather than "characters", so a post sitting near the line is not quietly mismeasured.

The send dialog also refuses an over-length Bluesky post now, rather than warning and sending
anyway, and says how many bytes over it is and why non-ASCII characters cost more. Every other
channel still warns without blocking: Mastodon's 500 is the default a server ships with rather
than a rule, and a hard stop built on a number the app is only guessing at would refuse posts
the server would have accepted. Bluesky's 300 is not a guess — past it, the send is a certain
failure.

This is deliberately stricter than Bluesky is. The app will refuse a post of 300 graphemes and
310 bytes that the network would accept, because the connector doing the posting will not. A
native Bluesky transport — the way Mastodon media already bypasses the automation engine —
would restore the real grapheme budget, and is the proper fix rather than this one.

## Verification

The complete backend suite passes: **259 tests**. Electron's main process and renderer pass
TypeScript checking, and the production desktop bundle builds successfully.

The connector's behaviour was read out of the running engine rather than inferred from its
symptoms, and the failing post was measured at 300 characters and 306 bytes against the
recorded automation run.

No live social post was made while verifying this release.

## Installing

These installers are unsigned. Windows SmartScreen and macOS Gatekeeper will both warn about
that — expected, not a sign anything is wrong. On Windows choose **More info → Run anyway**;
on macOS, right-click the app and choose **Open**.
